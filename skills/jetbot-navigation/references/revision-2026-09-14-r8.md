Date: 2026-09-14, America/Los_Angeles. Baseline and revisions1–7 are preserved.
This revision is experimental; see `reports/iteration-2026-09-14/` for both
successful and failed trials. The user reported an empty battery during this

battery sag contributed to their behavior. Do not treat those trials as motor

## Local tool division

`spatial_planner.py` performs bounded weighted search over camera x,z,yaw in an
explicitly inspected rectangle with retained obstacle rectangles. It chooses
forward/reverse drives (5–15cm), turns (up to30degrees), and small corrections
back to its heading grid. Search is bounded to one second/10,000 expansions.
It reports failure rather than returning a partial executable route. It does
not claim optimal paths or infer free space from missing detections.

`spatial_executor.py` executes up to four targets in the same map. It retains a
useful route suffix, verifies its sweeps from measured pose, and replans on
conflict or endpoint drift. Replanning every action originally caused forward/
reverse oscillation; that failed trace remains in `spatial-first.json`.
Limits:12 actions,60seconds,90cm travel, accumulated position sigma2cm and yaw
sigma4degrees. These uncertainty values are heuristic, not calibrated bounds.
Each drive retains15cm/two-second limits and all existing VIO, IMU, timing,
progress and lease guards. No VLM calls occur between actions or targets.

`spatial_turn.py` uses the proven60ms pulse/180ms rest policy at0.14, with
camera/IMU tracking during the turn and verified post-stop translation/yaw.
It uses generation-tagged commands, including zero-output commands between
pulses; an external stop cannot be overwritten by a later pulse. Turn sweeps
cover every fixed pivot inside the12x15cm chassis, requested angle plus5degrees
overrun,2degrees heading allowance,5cm clearance and2cm position allowance.
The7.5cm nominal pivot used in search is only a prediction. Execution measures
lens translation and never substitutes the nominal pivot for odometry.

`mapped_drive.py` is an opt-in (`measured_map_drive:true`) alternative under
validation. It checks nominal and measured chassis/braking geometry directly
against the retained map instead of a fixed wide segment rectangle. It is not
yet supported as a proven live navigation default. It does not detect new
objects, and discrete checks do not provide a formal continuous collision
guarantee. Do not widen maps or weaken guards just to make a plan pass.

An optional `initial_pose_cm_degrees` carries a measured pose in an existing
map, with `initial_position_variance_cm2` and `initial_yaw_variance_deg2`.
Reusing a map after a stopped experiment requires matching the new image to
the actual settled frame, verifying the control generation, retaining the
uncertainty, and inspecting for object movement. A reboot or handling
invalidates that continuity. Never reset uncertainty silently to reuse a map.

## One-terminal operating commands

Start the persistent supervisor (disarmed unless motion is authorized):

```bash
/usr/bin/python3 local_nav/maneuver_session.py --enable-motion --preview-directory /ABSOLUTE/WRITABLE/PREVIEW/DIRECTORY
```

Send newline-separated JSON on its stdin:

```json
{"command":"capture"}
{"command":"plan_navigation","image_path":"EXACT_RETURNED_CAPTURE_PATH","goals_cm":[[0,20],[0,0]],"inspected_free_rectangle_cm":[-20,-30,20,35],"obstacle_rectangles_cm":[],"goal_tolerance_cm":3}
```

The coordinates above are an example, not an assertion about the room. Supply
the actually inspected map, including offscreen chassis clearance. Planning
does not move the robot. Show the returned full-route preview before execution:

```json
{"command":"execute","plan":"RETURNED_PLAN_PATH","spatial":true}
{"command":"stop"}
{"command":"shutdown"}
```

`plan_navigation` binds targets to the exact latest capture and creates the
map/path preview. The supervisor remains responsive while its child executes.
`stop` revokes the motor generation and terminates the child. The service's
power watchdog independently blocks all motion commands.

Offline search and simulation:

```bash
/usr/bin/python3 local_nav/spatial_executor.py PLAN.json
/usr/bin/python3 local_nav/simulate_spatial.py --output REPORT.json
```

## Continuous supply-voltage protection

`battery.py` reads INA3221 channel1 (register0x02) at bus6/address0x40, verified
against the device-tree `POM_5V_IN`/`VDD_IN` label and chip IDs. It only reads
registers; it does not change driver limits or conversion settings. It checks
continuous bus conversion, channel enable and conversion period<=200ms before
accepting a sample. Actual configuration was0x7607, about53.8ms conversion.

The independent power worker samples about5Hz and appends time-stamped JSONL.
Three valid startup samples are required. Experiment policy: warn below4.9V;
latch motion off below4.8V, above5.5V, on missing/invalid telemetry or when the
last valid reading is older than0.6seconds. The motor worker checks this itself
at its10ms cadence; the supervisor is not required to notice first. A stalled
sensor process cannot indefinitely hold the motor worker on the shared lock.
After a fault, fresh voltage alone does not resume motors. Resolve the supply
problem and start a fresh service.

`status.power` and observations include voltage, sample time, warning/stop
state and minimum voltage. The supervisor logs voltage alongside each session,
emits state changes, and refuses a new route while power is blocked. Route and
turn logs also record start/end power readings. These are local checks with no
model requests.

**This is regulated Jetson input voltage, not battery charge.** `battery_percent`
stays null and `battery_state` states that no fuel gauge is available. A power
bank can maintain5V until abrupt cutoff, or the motors may have a separate
battery supply. Do not claim this protects against every empty-battery event.
The battery/power-board model was requested from the user to identify actual
charge telemetry. No fuel-gauge driver has been validated yet.

Read-only standalone check, without enabling motors:

```bash
/usr/bin/python3 local_nav/battery.py --seconds 10 --output power-check.jsonl
```

Hardware test with the service disarmed measured approximately5.00–5.08V,
healthy sensors and zero motor output; the service shut down cleanly. Fault
tests use a fake motor process and prove stopping/latching without deliberately
discharging the real battery.

References: [NVIDIA Nano power monitor and units](https://docs.nvidia.com/jetson/l4t/Tegra%20Linux%20Driver%20Package%20Development%20Guide/power_management_nano.html),
[TI INA3221 register definitions](https://www.ti.com/lit/ds/symlink/ina3221.pdf).
Voltage thresholds above are conservative experiment policy, not a battery
state-of-charge curve or a modification to NVIDIA's hardware limits.

## Other estimator changes and evidence

Quiet startup now uses at least150ms/six stable IMU samples to initialize up
within5degrees of calibration; ordinary direct-feed startup retains4degrees.
Acceleration std<=0.12m/s², mean norm within0.35m/s² of gravity and gyro<=1.5deg/s
are required. Duplicate frame recording preserves startup metadata and merges
IMU history instead of overwriting it. Replay honors that metadata.

Straight/batch pose checks use the expanded actual chassis and remaining coast
rather than an independent1cm lateral threshold. Existing heading, overrun,
clearance and uncertainty checks remain. Rejected poses are recorded explicitly.

Live evidence before the battery report:

- White-box batch reached16.048cm on a16cm request in3.024s command-to-result.
- New spatial executor completed two reverse10cm actions in4.422s, with final
  estimated pose[1.294,-19.704,-1.676deg],1.328cm target error and zero
  intermediate model requests.
- Round-trip attempt stopped after its first15.217cm drive because the next
  segment did not fit the retained map at the measured heading/lateral offset.
- A revised local search selected a2.167degree correction, executed it, then
  continued5.606cm without a model call between turn and drive. It reached the
  approach target but stopped before returning because no checked route fit.
  This was not a successful complete out-and-back mission.

Simulation `spatial-second.json` reached[30,30]cm with0.812cm ground-truth error
and zero intermediate model requests. It uses production planning, visual
tracking and drive/turn execution with rendered carpet, but directly simulated
IMU attitudes. Static obstacles are checked geometrically, not rendered or
recognized. Successful simulated drift recovery does not prove live recovery.
